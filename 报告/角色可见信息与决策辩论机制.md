# 角色可见信息与决策辩论机制

本文档总结当前代码版本中，四类董事会 Agent 能看到哪些信息、如何形成初始判断、辩论阶段能看到哪些过程信息，以及它们分别依据哪些角度进行辩论。

对应代码位置：

- 角色规则与可见字段：[boardroom_sim/roles.py](boardroom_sim/roles.py)
- Prompt 构造与 LLM 输出解析：[boardroom_sim/agents.py](boardroom_sim/agents.py)
- 模拟流程、辩论历史和最终聚合：[boardroom_sim/simulator.py](boardroom_sim/simulator.py)
- 数据结构定义：[boardroom_sim/models.py](boardroom_sim/models.py)

## 1. 总体信息边界

当前实验是一个正样本 VC 交易的时点回测。每个案例对应一家公司在真实 VC 交易发生前的董事会决策时点。

Agent 可以看到的信息分为四类：

1. 角色自己的四层规则：L1 目标、L2 注意字段、L3 启发式规则、L4 互动协议。
2. 角色可见的决策前字段：由 `layer_2_attention_fields` 控制。
3. 最小共享案例元数据：`case_id`、`company_label`、`company_id`、`decision_date`、`primary_industry`。
4. 董事会上下文：已经发言角色的立场摘要，辩论阶段还包括历史发言记录和当前综合提案。

Agent 不应看到的信息：

- 当前目标交易真实结果，例如真实融资额、真实交易类型、真实完成状态、真实估值等。这些只存在于 `notes.labels`，用于后续评测。
- `business_status`、`company_financing_status`、`ownership_status` 这类 PitchBook 当前快照状态字段。它们可能泄露未来状态，目前不进入任何角色的可见字段。
- 缺失数值以 JSON `null` 传入 prompt。Prompt 明确要求：`null` 表示缺失或未观测，不能当作 `0`。

## 2. Agent 输出字段

每个角色需要输出以下判断：

| 字段 | 含义 | 当前允许值 |
| --- | --- | --- |
| `financing_intent` | 是否现在发起融资 | `raise_now`、`wait`、`avoid` |
| `completion_view` | 如果现在融资，交易是否可能完成 | `likely_complete`、`unlikely_complete` |
| `predicted_deal_size_usd_m` | 预测融资额，单位百万美元 | 非负数字；若 `raise_now`，必须大于 0 |
| `predicted_deal_type` | 预测交易类型 | `Seed Round`、`Early Stage VC`、`Later Stage VC`、`Bridge`、`Debt`、`Other` |
| `valuation_direction` | 预测估值方向 | `up`、`flat`、`down` |
| `ceo_replacement_view` | 对 CEO 是否更换的观点 | `keep`、`monitor`、`replace` |
| `satisfaction_score` | 该角色对当前判断/提案的满意度 | 0-100 |
| `rationale` | 简短理由列表 | 字符串列表 |

硬性规则：

- 如果 `financing_intent = raise_now`，则 `predicted_deal_size_usd_m > 0`。
- 如果 `financing_intent = wait` 或 `avoid`，则 `predicted_deal_size_usd_m` 可以为 0。
- `completion_view` 不再允许 `uncertain`。
- `valuation_direction` 不再允许 `unknown`。
- 如果模型仍返回非法标签，解析代码会用默认值纠正：`completion_view -> likely_complete`，`valuation_direction -> flat`。

## 3. 决策流程

### 3.1 初始判断阶段

代码位置：`BoardroomSimulator.simulate()` 调用 `BoardAgent.evaluate()`。

四个角色按固定顺序依次做初始判断：

1. `Founder_CEO`
2. `CTO`
3. `Lead_VC_Director`
4. `Followon_VC_Director`

每个角色初始判断时会收到：

- system prompt：要求严格遵守四层角色规则，只用可见决策前字段，只返回 JSON。
- user prompt：
  - 当前角色名称；
  - 完整四层角色规则；
  - 该角色自己的可见字段；
  - 最小共享案例元数据；
  - 已经完成初始判断的前序角色立场摘要，即 `context_payload_json`。

初始阶段的 `context_payload_json` 是顺序累积的：

- `Founder_CEO` 看到 `{}`。
- `CTO` 看到 `Founder_CEO` 的初始判断。
- `Lead_VC_Director` 看到 `Founder_CEO` 和 `CTO` 的初始判断。
- `Followon_VC_Director` 看到前三个角色的初始判断。

### 3.2 开场陈述阶段

每个角色基于自己的初始判断生成一条简短开场陈述，写入 trace。

注意：开场陈述本身不单独发送给 LLM，也不会进入 `prior_messages_json`。它主要用于过程记录和报告展示。

### 3.3 辩论阶段

代码位置：`BoardroomSimulator._run_bargaining_round()` 调用 `BoardAgent.bargaining_step()`。

每一轮辩论仍按固定角色顺序进行。每个角色发言时会收到：

- 角色自己的四层规则；
- 角色自己的可见字段；
- 当前综合提案 `proposal_json`；
- 自己当前判断 `current_prediction_json`；
- 所有角色当前最新立场 `context_payload_json`；
- 此前所有辩论发言 `prior_messages_json`。

角色需要输出：

- 一段 1-3 句的董事会辩论发言 `message`；
- 更新后的完整判断。

每个角色发言后，代码会立即更新：

```python
context[role_name] = updated_decision
```

因此，后续角色看到的是已经被前面角色更新过的最新董事会状态。

## 4. 辩论过程信息

### 4.1 `context_payload_json`

`context_payload_json` 是当前董事会上下文，按角色名组织，每个角色包含其最新立场摘要：

```json
{
  "Founder_CEO": {
    "financing_intent": "raise_now",
    "completion_view": "likely_complete",
    "predicted_deal_size_usd_m": 40.0,
    "predicted_deal_type": "Early Stage VC",
    "valuation_direction": "flat",
    "ceo_replacement_view": "keep",
    "satisfaction_score": 70,
    "rationale": ["reason 1", "reason 2"]
  }
}
```

生成代码：`BoardAgent._decision_payload()`。

### 4.2 `prior_messages_json`

`prior_messages_json` 是此前所有辩论发言历史。每条记录包括：

```json
{
  "round": 1,
  "role": "Founder_CEO",
  "message": "I support a focused financing round...",
  "updated_decision": {
    "role_name": "Founder_CEO",
    "financing_intent": "raise_now",
    "completion_view": "likely_complete",
    "predicted_deal_size_usd_m": 40.0,
    "predicted_deal_type": "Early Stage VC",
    "valuation_direction": "flat",
    "ceo_replacement_view": "keep",
    "satisfaction_score": 70,
    "rationale": ["reason 1", "reason 2"],
    "observed_fields": {}
  }
}
```

生成代码：`BoardroomSimulator._run_bargaining_round()`。

需要注意：当前 `updated_decision` 中包含 `observed_fields`。这意味着后续角色可能通过辩论历史间接看到前序角色的可见字段。如果后续希望更严格的信息隔离，可以把 `prior_messages_json` 中的 `updated_decision` 改为只保留 `_decision_payload()` 摘要。

### 4.3 `proposal_json`

`proposal_json` 是根据所有角色当前判断聚合出的当前综合提案，包含：

| 字段 | 含义 |
| --- | --- |
| `recommended_deal_size_usd_m` | 综合建议融资额，单位百万美元 |
| `recommended_deal_type` | 综合建议交易类型 |
| `valuation_direction` | 综合估值方向 |
| `estimated_dilution_pct` | 根据预测融资额和上一轮投后估值估算的稀释比例；若估值缺失则为 `null` |
| `investor_protection_level` | 投资人保护强度：`light`、`standard`、`strong` |
| `tech_budget_protected` | 技术预算是否被保护 |
| `ceo_milestones_required` | 是否需要 CEO milestone 约束 |

生成代码：`BoardroomSimulator._build_proposal()`。

## 5. 各角色可见字段与判断角度

### 5.1 Founder_CEO

Founder_CEO 的核心目标：

- 最大化公司长期价值和退出价值。
- 维持创始人控制权。
- 保持执行自由，尽量减少重大经营事项上的 veto 触发。

可见字段：

| 字段 | 含义 |
| --- | --- |
| `prior_deal_size_usd_m` | 上一笔 VC 融资金额 |
| `prior_post_money_valuation_usd_m` | 上一笔 VC 投后估值 |
| `prior_valuation_markup_multiple` | 上一笔估值相对再上一笔估值的倍数 |
| `prior_valuation_direction_label` | 上一笔历史估值方向 |
| `prior_deal_type` | 上一笔交易类型 |
| `prior_vc_round` | 上一笔 VC 轮次标签，作为历史信息 |
| `prior_raised_to_date_usd_m` | 上一笔融资后累计融资额 |
| `prior_investor_ownership_pct` | 上一笔融资后投资人持股比例 |
| `prior_lead_investor_count` | 上一笔领投方数量 |
| `prior_lead_investor_types` | 上一笔领投方类型 |
| `employee_count_at_decision` | 决策时点前最近员工数 |
| `employee_growth_rate` | 员工增长率 |
| `founder_count` | 创始人数量 |
| `current_ceo_is_founder` | 当前 CEO 是否为创始人 |
| `board_member_count` | 董事会成员数量 |
| `investor_board_member_count` | 投资人董事数量 |

判断和辩论角度：

- 是否需要现在融资来换取增长资源、战略价值或生存概率。
- 融资是否会威胁创始人控制权、董事会影响力或 CEO 任期。
- 稀释是否可以接受，前提是资本能带来足够增长资源。
- 历史估值方向和 markup 是否会影响下一轮融资的政治成本。
- 对投资人让步时，需要强调控制权底线和执行自由。

### 5.2 CTO

CTO 的核心目标：

- 保护工程团队健康、招聘预算和技术债预算。
- 保证技术可行性和产品里程碑可交付。
- 维护技术声誉和技术决策权。

可见字段：

| 字段 | 含义 |
| --- | --- |
| `prior_deal_size_usd_m` | 上一笔 VC 融资金额 |
| `prior_raised_to_date_usd_m` | 上一笔融资后累计融资额 |
| `employee_count_at_decision` | 决策时点前最近员工数 |
| `previous_employee_count` | 上一条员工数记录 |
| `employee_growth_rate` | 员工增长率 |
| `engineering_role_count` | 可识别的工程/技术岗位人数 |
| `executive_role_count` | 可识别的高管岗位人数 |
| `primary_industry` | 主行业 |
| `industry_group` | 行业组 |
| `industry_sector` | 行业部门 |
| `verticals` | 垂直赛道标签 |
| `keywords` | 公司关键词 |
| `description` | 公司业务描述 |
| `company_age_at_decision_years` | 决策时点公司年龄 |

判断和辩论角度：

- 融资是否能保护工程团队、招聘、基础设施和技术债预算。
- 如果融资会挤压工程资源或逼迫短期技术妥协，则倾向反对、等待或缩小规模。
- 行业和业务描述是否意味着资本密集型研发或基础设施扩张需求。
- 是否存在工程团队不足、技术岗位过少或增长信号缺失。
- 辩论中应披露技术债、招聘困难、架构风险和产品里程碑风险。

### 5.3 Lead_VC_Director

Lead VC 的核心目标：

- 最大化基金退出倍数，并保持领投方定价纪律。
- 获取有利条款，包括下行保护、反稀释和董事席位。
- 保护组合公司的 markup 信号，以利于未来募资。

可见字段：

| 字段 | 含义 |
| --- | --- |
| `prior_post_money_valuation_usd_m` | 上一笔投后估值 |
| `prior_pre_money_valuation_usd_m` | 上一笔投前估值 |
| `prior_valuation_markup_multiple` | 上一笔估值倍数 |
| `prior_valuation_direction_label` | 上一笔估值方向 |
| `prior_deal_size_usd_m` | 上一笔融资金额 |
| `prior_raised_to_date_usd_m` | 累计融资额 |
| `prior_investor_ownership_pct` | 投资人持股比例 |
| `prior_investor_count` | 上一笔投资人总数 |
| `prior_new_investor_count` | 上一笔新投资人数量 |
| `prior_followon_investor_count` | 上一笔跟投投资人数量 |
| `prior_lead_investor_count` | 上一笔领投方数量 |
| `prior_lead_investor_amount_share` | 上一笔领投方披露金额占比 |
| `prior_lead_preferred_deal_size_min_usd_m` | 上一笔领投方偏好投资额下限 |
| `prior_lead_preferred_deal_size_max_usd_m` | 上一笔领投方偏好投资额上限 |
| `prior_lead_preferred_company_valuation_min_usd_m` | 上一笔领投方偏好估值下限 |
| `prior_lead_preferred_company_valuation_max_usd_m` | 上一笔领投方偏好估值上限 |
| `employee_growth_rate` | 员工增长率 |
| `similar_company_count` | 相似公司数量 |
| `board_member_count` | 董事会成员数量 |
| `investor_board_member_count` | 投资人董事数量 |

判断和辩论角度：

- 当前融资额和估值方向是否符合定价纪律。
- 如果风险高，是否需要更强下行保护、反稀释、董事席位或 CEO milestone。
- 历史估值倍数、上一轮融资额、累计融资额和员工增长是否支持继续融资。
- 是否存在 fund concentration 或单笔过度暴露风险。
- 当治理风险上升时，应通过条款和董事会影响力保留管理层更换选项。

### 5.4 Followon_VC_Director

Follow-on VC 的核心目标：

- 保护 pro-rata 权利，避免被领投方稀释。
- 在较小、更分散的风险暴露下保护投资 IRR。
- 维护组合分散性和与优质领投方共同投资的信号价值。

可见字段：

| 字段 | 含义 |
| --- | --- |
| `prior_deal_size_usd_m` | 上一笔融资金额 |
| `prior_post_money_valuation_usd_m` | 上一笔投后估值 |
| `prior_valuation_markup_multiple` | 上一笔估值倍数 |
| `prior_valuation_direction_label` | 上一笔估值方向 |
| `prior_investor_ownership_pct` | 投资人持股比例 |
| `prior_investor_count` | 上一笔投资人总数 |
| `prior_followon_investor_count` | 上一笔跟投投资人数量 |
| `prior_lead_investor_count` | 上一笔领投方数量 |
| `prior_lead_investor_types` | 上一笔领投方类型 |
| `prior_lead_investor_amount_share` | 上一笔领投方披露金额占比 |
| `prior_lead_preferred_deal_size_min_usd_m` | 上一笔领投方偏好投资额下限 |
| `prior_lead_preferred_deal_size_max_usd_m` | 上一笔领投方偏好投资额上限 |
| `employee_growth_rate` | 员工增长率 |
| `similar_company_count` | 相似公司数量 |

判断和辩论角度：

- 默认倾向跟投；不跟投需要明确理由，例如估值恶化、公司信号变差、基金时点不匹配。
- 是否需要为了防止股权被稀释而支持融资。
- 是否应抵制领投方提出的、损害跟投方权益或清算优先级的条款。
- 领投方质量和投入强度是重要信号。
- 单笔投资额和行业集中度不能为单个机会轻易突破。

## 6. 最终聚合机制

辩论结束后，模拟器不会再调用 LLM，而是用确定性规则聚合最终结果。

### 6.1 角色权重

```python
ROLE_WEIGHTS = {
    "Founder_CEO": 2.0,
    "CTO": 0.5,
    "Lead_VC_Director": 3.0,
    "Followon_VC_Director": 1.5,
}
```

### 6.2 聚合字段

- `financing_initiation_decision`：按角色权重选择 `financing_intent` 的加权多数。
- `financing_completion_view`：按角色权重选择 `completion_view` 的加权多数。
- `predicted_deal_size_usd_m`：对非 `avoid` 且融资额大于 0 的角色预测进行加权平均。
- `predicted_deal_type`：按角色权重选择交易类型。
- `valuation_direction`：按角色权重选择估值方向。
- `ceo_replacement_decision`：使用单独治理规则聚合 CEO 更换压力。
- `consensus_score`：计算核心字段上的一致度。
- `deal_break_risk`：由融资意向、完成判断和共识分数映射。
- `governance_conflict_risk`：由 CEO 更换压力和投资人压力映射。

## 7. 当前设计中需要注意的问题

1. `prior_messages_json` 中的 `updated_decision` 当前包含 `observed_fields`，可能造成角色间间接共享部分私有可见字段。
2. `business_status`、`company_financing_status`、`ownership_status` 仍保留在 `BoardCase` 里用于审计，但不进入角色可见字段。
3. `prior_vc_round` 仍作为历史输入字段存在，但模型不再预测 `predicted_vc_round`。
4. `completion_view` 被强制二分类，模型必须在 `likely_complete` 与 `unlikely_complete` 中选择。
5. `valuation_direction` 被强制三分类，模型必须在 `up`、`flat`、`down` 中选择。
